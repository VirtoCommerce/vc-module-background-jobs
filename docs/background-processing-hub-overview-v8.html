SECTION 01

Why move
off Hangfire?

The problem is not Hangfire. The problem is that it is the only option and its API has leaked across the Platform and every module.

Problem · Coupling

Hangfire has leaked everywhere

It is not isolated in one place. The same patterns — enqueue, recurring, cancellation, context, concurrency, retry, progress — were each reinvented against Hangfire's surface. A breaking change ripples through all of them.

Platform & modules bound to Hangfire

  • Platform — IRecurringJobService → Hangfire IRecurringJobManager
  • Import — BackgroundJob.Enqueue, PerformContext, IJobCancellationToken
  • Bulk Actions — a duplicate IBackgroundJobExecutor
  • Subscription — [DisableConcurrentExecution]

The seven patterns to abstract

Enqueue Recurring / cron Cancellation token Per-job context Concurrency guard Automatic retry Progress push

These map almost 1:1 to the features we need. Abstract them once, and the engine behind them becomes a choice — not a constraint.

The scaling problem. Hangfire is a pull model: workers must run the same code base and poll shared storage. No scale-to-zero, idle workers still cost, and the unit of scale is "another full Platform instance." For bursty work like a full catalog reindex this is slow and expensive.

SECTION 02

A passive Platform,
pluggable engines

Introduce a small Core abstraction the Platform and all modules depend on. Engines live in separate packages behind one port, chosen by configuration.

Solution · First Principle

Messages, not delegates

This is the single most important design decision. Providers fall into two camps, and the contract must serve both without favouring either.

Pull / worker model

Hangfire · Quartz · Temporal workers

Platform writes a job to shared storage. Worker instances poll and run the same .NET code in-process. Scale = more instances.

Push / dispatch model

Cloud Run · ACA Jobs · Lambda

Platform pushes an event to an external runtime that scales to zero. The job calls back into the Platform REST API to do the work.

The decision. The payload that crosses the boundary must be a serializable message, never an Expression<Func<T,Task>>. The pull adapter turns it back into a method call; the push adapter turns it into an HTTP dispatch. If Core leaks expressions, we have rebuilt the Hangfire coupling under a new name.

Solution · Principles

Eight principles

Everything in the design follows from these. They are the lens for reviewing every adapter we add later.

01Platform is passive. It enqueues and orchestrates; engines execute. It must run as nothing but a callback target.
02Depend on contracts, not engines. No module references Hangfire.* or any provider type.
03Messages, not delegates. Work crosses every boundary as a serialized envelope.
04One port, many adapters. Hexagonal — same pattern as cache, search, storage providers.
05Idempotency is a default. Push is at-least-once; dedup keys and idempotent handlers are built in.
06Observe once, everywhere. One OpenTelemetry model across every engine and boundary.
07Claim-check large data. Store the blob, pass a reference — imports already work on file URLs.
08Backward compatible first. Ship with Hangfire as the only engine, zero behaviour change, then add engines.
SECTION 03

The architecture
at a glance

Three layers. Modules depend only on contracts. The Hub owns serialization, progress, telemetry, and the callback API. Providers are swappable adapters.

Architecture · Layers

Modules · Hub · Providers

Each layer has one job. Modules enqueue through contracts; the Hub serializes and dispatches; the chosen provider executes — in-process or via an external runtime.

Architecture · Data Flow

One call, two paths

The enqueue call is identical at the call site. It diverges only inside the provider adapter — and both paths converge on SignalR for admin progress.

Architecture · Push Model

The external job holds no business logic

In the push model the container is a generic, stable trigger. It relays the job to the Platform callback endpoint, where the real handler runs in-process. This is exactly why a fresh instance can be spun up purely to serve callbacks.

Why this matters. The container image never changes when business jobs change — the same image serves every job type. Workers are separate from the web tier, so a bad job deploy doesn't recycle the storefront, and load scales independently.

Providers · In-the-box Default

What ships in Docker by default

The question splits into two roles: the broker (what lives in the container) and the scaler (what gives scale-to-zero). Cloud Run / ACA fuse both — which is why they can't be the in-box default. They live outside Docker.

Broker · RabbitMQ

Native ACK/NACK, retry, dead-letter queues. Durability that Redis pub/sub can't match for jobs. First-class Docker image; AMQP is a stable contract for a .NET worker.

Worker · MassTransit

A .NET consumer container drains the queue and calls the dispatcher. Same code and broker across dev and prod — only the scaler wrapper changes.

Scaler · KEDA

Scale-from-zero on RabbitMQ queue length — on Kubernetes only. KEDA is a K8s operator, not a Compose component.

Compose tier (dev / small prod)

RabbitMQ + N fixed worker replicas. No scale-to-zero — works out of the box, no Kubernetes.

Kubernetes tier (the scaling story)

Same RabbitMQ + same image + KEDA ScaledObject → true scale-from-zero. Cloud brokers (Service Bus, Pub/Sub) swap in by config.

Providers · The Default Broker

Why RabbitMQ is the proposal

RabbitMQ sits between the two models: it is the broker that ships in the Docker image, and it can run pull (a hosted consumer drains it in-process) or push (KEDA spins up workers that call back). One broker, both deployment stories.

What makes it the right default

  • Durable queues + persistent messages — jobs survive a broker restart. The property Redis pub/sub can't give.
  • Per-message ACK / NACK — at-least-once with explicit redelivery control.
  • Dead-letter exchange — poison messages don't block the queue; they stay inspectable.
  • Delayed-message plugin — native delayed jobs via x-delay.
  • First-class Docker image — AMQP is a stable contract for a .NET worker.

Pre-reqs: management plugin enabled (health + KEDA read queue depth) and rabbitmq_delayed_message_exchange for delays. Both ship as flags on the Docker image.

SECTION 04 · CLOUD

Virto Cloud:
multi-tenant & observable

How RabbitMQ + KEDA land in Virto Cloud for many clients at once — and what replaces the Hangfire dashboard for monitoring it.

Cloud & Ops · Multi-Tenancy

One cluster, isolated per tenant

A shared RabbitMQ cluster partitions tenants by vhost — each client gets its own queues, users, and permissions, fully isolated. KEDA watches each tenant's queue depth and scales that tenant's worker deployment independently, so one client's reindex never starves another's order processing.

Isolation by vhost

Per-tenant vhost + user + permissions. A noisy tenant can't read or flood another's queues.

Independent scaling

One ScaledObject per tenant; each worker pool scales 0→N on its own queue depth + resource quota.

Fair use & cost

Per-tenant max replicas cap spend and stop one client monopolizing the cluster. GitOps-managed via Flux.

Cloud & Ops · KEDA Impact

KEDA barely touches IJobEngine

The surprising part: KEDA is a scaler, not a transport — it never sits in the message path. Enqueue is byte-for-byte identical with or without it. What KEDA changes is the consumer's lifecycle and the deployment shape — and it lives entirely in YAML, never in the engine.

Enqueue (publish)—unchanged

The one real code change: harden shutdown. Under scale-to-zero the consumer is killed routinely, not just on deploys — a SIGTERM mid-job must NACK-and-requeue, never drop the message.

# change it without recompiling the app.

  name: indexing-worker-scaler

  scaleTargetRef:
    name: vc-background-worker   # the consumer
  minReplicaCount: 0            # scale to zero
  maxReplicaCount: 50
  triggers:

        queueName: indexing
        mode: QueueLength

      authenticationRef:
        name: rabbitmq-auth

Two flavours: ScaledObject scales a long-running Deployment (consumer needs graceful drain); ScaledJob runs a K8s Job per batch (consumer becomes "process N, then exit").

Why this matters. The engine stays a clean AMQP publisher; KEDA is a deployment concern layered on top. That separation is exactly what lets the same RabbitMqJobEngine run unmodified in Compose (fixed workers) and Kubernetes (KEDA-scaled 0→N) — only the consumer's shutdown handling and a YAML file differ.

Cloud & Ops · Observability

What replaces the Hangfire dashboard

The Hangfire dashboard was one in-process UI. A provider-agnostic, multi-tenant system needs layered observability — a global ops view for the platform team and an application view inside Virto Commerce for tenant admins. Both read from the same engine-independent telemetry.

Global level — platform / SRE

  • Prometheus — scrapes the built-in rabbitmq_prometheus plugin (auto-enabled by the Cluster Operator) + KEDA + worker metrics.
  • Grafana — queue depth, message/ack rates, consumer health, pod scaling per tenant vhost.
  • Alertmanager — queue-backlog & DLQ alerts → Slack / PagerDuty.
  • Jaeger / Tempo — OpenTelemetry traces spanning enqueue → dispatch → execute → callback.

Application level — tenant admin

  • Live progress reuse — feeds the existing push-notification UI (progress bars in the admin) via IJobProgress.
  • Jobs blade new — running / queued / failed list, retry & cancel — a blade inside the existing admin.
  • DLQ inspector new — view, replay, or discard dead-lettered jobs.
  • Health API + trace links — IBackgroundProcessingHealth; jump from a failed job to its trace.

One source, two audiences. Everything is built on OpenTelemetry emitted by the Hub — the same job.duration, queue.lag, retry.count metrics regardless of engine. Add to Virto Cloud: Prometheus, Grafana, Alertmanager, Jaeger/Tempo, the RabbitMQ Cluster Operator. Add to Virto Commerce: the Jobs admin blade, health API, and DLQ inspector. Switching engine later changes nothing the operator sees.

Mostly reuse, partly build. The tenant-admin view is a new module inside the existing Virto Commerce admin — not a standalone application, and not fully off-the-shelf. SECTION 05

The C#
developers write

Two audiences. Module authors write handlers and enqueue calls. Provider implementers write one adapter against the port.

Code · Module Authors

Define a job, enqueue it — extendable by default

The enqueue is handler-explicit — Enqueue<THandler>(payload) names the action at the call site, so it reads clearly in review and one payload can drive several handlers. The payload is an AbstractTypeFactory type (not a sealed record) so partners extend it without forking.

// Payload — overridable type, NOT a sealed record
public class SendOrderEmailPayload : ValueObject
{
  public string OrderId { get; set; }
  public string CustomerEmail { get; set; }
}

// Handler — implements IBackgroundJobHandler<TPayload>
public class SendOrderEmailJob(
    IEmailSender sender, IOrderService orders)
  : IBackgroundJobHandler<SendOrderEmailPayload>
{
  public async Task Execute(
      SendOrderEmailPayload p,
      IJobExecutionContext ctx, CancellationToken ct)
  {
    var order = await orders.GetByIdAsync(p.OrderId);
    await sender.SendConfirmationAsync(
        p.CustomerEmail, order, ct);
  }
}

// Register — payload inferred from the handler
services.AddBackgroundJob<SendOrderEmailJob>();
// Enqueue — build payload via the factory so a
// partner's derived type flows through end-to-end
var p = AbstractTypeFactory<SendOrderEmailPayload>
    .TryCreateInstance();
p.OrderId = order.Id; p.CustomerEmail = order.Email;

await jobs.Enqueue<SendOrderEmailJob>(p);   // names the handler

// With options — queue · progress · dedup key
await jobs.Enqueue<ReindexProductJob>(reindexPayload,
  new EnqueueOptions
  {
    Queue          = "indexing",
    ReportProgress = true,
    UniqueKey      = $"reindex:{productId}",  // engine-dependent
  });

// One payload, several handlers — the enqueue
// names which one runs (a partner registers its own)
services.AddBackgroundJob<AcmeSendOrderEmailJob>();
await jobs.Enqueue<AcmeSendOrderEmailJob>(p);

// Extend the payload — AbstractTypeFactory, as ever
AbstractTypeFactory<SendOrderEmailPayload>
  .OverrideType<SendOrderEmailPayload, AcmePayload>();

Extendable from the start. Because the payload is created through AbstractTypeFactory and handlers resolve from DI, a partner extends the payload (OverrideType) and ships its own handler using the same tools they already use across Virto — no sealed types, no Hub fork. Recurring follows the same shape via AddRecurringJob<THandler, TPayload>; an event→job binder is on the roadmap.

Code · Provider Implementers

One port, one envelope

Every engine implements IJobEngine. Work crosses the boundary as a serialized envelope — a message, never a delegate. This is what makes push providers possible.

public interface IJobEngine
{
  string ProviderName { get; }

  Task<string> Enqueue(
      JobEnvelope envelope, EnqueueOptions options,
      CancellationToken ct = default);

  Task<Job?> GetStatus(string jobId, ...);
  Task<bool> Delete(string jobId, ...);
}

// Recurring is a separate, optional port:
public interface IRecurringJobScheduler
{
  Task AddOrUpdate(
      RecurringJobRegistration r, string cron, ...);
  Task Remove(string id, ...);
}
// The serialized unit of work — a message.
public sealed class JobEnvelope
{
  public string JobType { get; set; }     // payload contract
  public string HandlerType { get; set; } // which handler
  public string PayloadType { get; set; } // concrete type
  public string PayloadJson { get; set; }

  // at-least-once → collapse duplicates (engine-dependent)
  public string? UniqueKey { get; set; }

  // enqueuing user, restored on the worker
  public string? UserName { get; set; }

  public int Attempt { get; set; } = 1;
}

Shared execution path. The Hub provides IJobDispatcher.Dispatch(envelope, context, ct) — deserialize the payload, open a per-job DI scope, resolve the IBackgroundJobHandler<> (by handler type), run it, and restore the enqueuing user. Pull engines call it inside the job method; push engines call it from the callback controller. A job runs identically no matter who dispatched it.

Code · Push Round-Trip

Dispatch, then call back

The ACA adapter enqueues to Service Bus; KEDA scales from zero. The generic container relays to the Platform callback, where the real work runs in-process under an idempotency guard.

// PUSH adapter — enqueue to Service Bus
public async Task<string> Enqueue(
    JobEnvelope env, EnqueueOptions opt, ...)
{
  var jobId = Guid.NewGuid().ToString("N");
  await using var sender =
      bus.CreateSender(_opt.QueueName);

  var dispatch = new AcaDispatch {
    JobId = jobId, Envelope = env,
    CallbackUrl = $"{_opt.BaseUrl}/api/.../callback" };

  var msg = new ServiceBusMessage(
      JsonSerializer.SerializeToUtf8Bytes(dispatch))
    { MessageId = env.DeduplicationKey ?? jobId };

  await sender.SendMessageAsync(msg, ct);
  return jobId; // KEDA scales the job
}
// Platform callback — the REAL work runs here
[HttpPost("callback")]
public async Task<IActionResult> RunCallback(
    JobCallbackRequest req, CancellationToken ct)
{
  var key = req.Envelope.DeduplicationKey ?? req.JobId;
  if (!await dedup.TryBeginAsync(key, ct))
    return Ok(/* already processed */);

  try {
    await dispatcher.DispatchAsync(req.Envelope, ctx, ct);
    await dedup.MarkCompletedAsync(key, ct);
    return Ok();
  } catch (Exception ex) {
    await dedup.ReleaseAsync(key, ct);
    return StatusCode(500); // provider retries
  }
}

Config-driven selection. BackgroundProcessing:Provider = "Hangfire" | "CloudRun" | "AzureContainerApps" picks the engine at startup — the same pattern as cache, search, and storage providers. Switching engines is an appsettings.json change, not a recompile.

Code · Recurring & Scheduled

Recurring jobs, with a validated Cron setting

A recurring job is a handler + a schedule, registered with AddRecurringJob<THandler, TPayload>. The cron can be fixed (.WithCron) or setting-driven (.FromSettings) — and setting-driven crons use the new SettingValueType.Cron, so a hand-written expression is validated on save and edited with presets + a live plain-English description.

// Fixed cron — handler-explicit, readable
services.AddRecurringJob<ReindexCatalogJob, ReindexPayload>(
  () => new ReindexPayload { CatalogId = id },
  schedule => schedule
    .WithId("Catalog.Reindex")
    .WithQueue("indexing")
    .WithCron("0 */6 * * *")          // 5- or 6-field
    .WithTimeZone("Europe/Berlin"));

// Setting-driven — enabler + cron from platform
// settings; re-applied live when either changes.
services.AddRecurringJob<ProcessSubscriptionJob,
                         SubscriptionPayload>(
  schedule => schedule
    .WithId("Subscription.ProcessJob")
    .FromSettings(
      Settings.EnableSubscriptionJob,   // Boolean
      Settings.CronSubscriptionJob));   // Cron
// The cron lives in a Cron-typed SETTING:
public static readonly SettingDescriptor
  CronSubscriptionJob = new()
{
  Name         = "…CronSubscriptionJob",
  ValueType    = SettingValueType.Cron,  // ← new
  DefaultValue = "0 */6 * * *",
};

// On save the platform validates it (Cronos,
// 5/6-field) — a typo is REJECTED, never a
// silently-disabled job.

// In the admin UI the Cron editor shows:
//  • a preset picker (Every hour, Daily 07:00…)
//  • a live plain-English description (cronstrue):
//      "0 7 * * *"  →  "At 07:00, every day"

Why a Cron setting type. It validates on save (a typo can't silently disable a job) and the admin edits it with a preset picker + live description instead of memorizing cron. On non-Hangfire engines the in-process scheduler fires each occurrence fleet-safe exactly-once (distributed lock + shared occurrence marker), bounded-retries a transient enqueue failure rather than dropping the tick, and runs under a system:{jobId} identity.

Code · Overlap & Engine Routing

Never run the same job on top of itself

If a 6-hourly reindex takes 7 hours, the next tick must not launch a second run. The overlap policy is enforced by the Hub via a distributed lock keyed on the job id — so it holds across every worker instance, not just one process.

public enum OverlapPolicy
{
  Allow,    // concurrent runs permitted (default off)
  Skip,     // tick fires while running → skip this tick
  Queue,    // run sequentially after the current one
  Cancel,   // cancel the in-flight run, start fresh
}

// Enforced centrally before dispatch:
await using var lease = await _locks.TryAcquireAsync(
    $"recurring:{jobId}", ttl: TimeSpan.FromHours(2));

if (lease is null)                 // already running elsewhere
{
  if (policy == OverlapPolicy.Skip)
      { _log.SkipOverlap(jobId); return; }
  if (policy == OverlapPolicy.Queue)
      { await _scheduler.DeferAsync(jobId); return; }
}
await _dispatcher.DispatchAsync(envelope, ctx, ct);

Distributed, not per-process

The lock lives in the shared store (SQL / Redis), so overlap is prevented across the whole worker fleet — the case Hangfire's [DisableConcurrentExecution] only partly covered.

Self-healing via TTL

The lease has a TTL. If a worker dies mid-run, the lock auto-expires — a stuck job can never block the schedule forever.

Misfire handling

Misfire.RunOnceOnRecovery coalesces missed ticks (downtime) into a single catch-up run instead of a thundering herd.

Where cron lives per engine. Hangfire → its recurring manager (+ Hub lock for true overlap safety). RabbitMQ → the Hub scheduler ticks and publishes. Cloud Run → Cloud Scheduler. ACA → a scheduled job trigger. Module code is identical across all of them.

Code · Scaling Pattern

Map / Reduce for enterprise fan-out

Full-catalog indexation today is one long job grinding through everything in sequence. Map/Reduce splits it into N independent partitions any worker can pick up in parallel, then a reduce step finalizes — e.g. a blue-green index swap.

On Hangfire

Batches + continuations — the reduce runs when all maps finish.

On Cloud Run / ACA

A parallel job with task-count; a final reduce task.

On Temporal

Native fan-out with checkpoint/replay if a worker dies mid-run.

Code · Map/Reduce on RabbitMQ

Two handlers, one enqueue

The developer writes a map handler and a reduce handler and enqueues by naming them — the item/result/state types are derived from the handler interfaces. The Hub fans out one message per item, drains them in parallel across workers, and triggers the single reduce when all items settle. Contracts ship in Platform.Core; no direct RabbitMQ code.

1 · MAP HANDLER
// One page of ids → a small result.
// Runs in parallel across all workers.
public class IndexPageHandler(
    IIndexingManager indexer)
  : IMapJobHandler<IndexPage,
                   IndexPageResult>
{
  public async Task<IndexPageResult> Map(
      IndexPage page,
      IJobExecutionContext ctx,
      CancellationToken ct)
  {
    var failed = await indexer
      .IndexDocuments(page.DocumentType,
                      page.DocumentIds, ct);
    return new IndexPageResult(
      page.DocumentIds.Length - failed.Length,
      failed);
  }
}
2 · REDUCE HANDLER
// Runs ONCE, after every page reaches
// a terminal state — gets each page's
// MapResult<T> plus the shared state.
public class IndexSummaryReducer
  : IReduceJobHandler<IndexSummary,
                      IndexPageResult>
{
  public Task Reduce(
      IndexSummary state,
      IReadOnlyCollection<
        MapResult<IndexPageResult>> results,
      IJobExecutionContext ctx,
      CancellationToken ct)
  {
    var indexed = results
      .Where(r => r.Succeeded)
      .Sum(r => r.Value!.Indexed);
    // swap alias · re-index failed ids …
    return Task.CompletedTask;
  }
}
3 · REGISTER + ENQUEUE
// Register the pair (module Initialize)
services.AddMapReduceJob<
    IndexPageHandler, IndexSummaryReducer>();

// Enqueue — NAME the handlers; item/
// result/state are derived from them
// and validated. Partition into PAGES.
var pages = allIds.Chunk(50)
  .Select(ids => new IndexPage("Product", ids));

await mapReduce.Enqueue<
    IndexPageHandler, IndexSummaryReducer>(
  items: pages,
  state: new IndexSummary("Product",
      DateTime.UtcNow.Ticks),
  options: new MapReduceOptions {
    Queue = "indexing",
    FailurePolicy =
      FailurePolicy.ContinueOnError,
    ReportProgress = true });

Two contracts, one enqueue. IMapJobHandler<TItem,TResult> runs per item in parallel; IReduceJobHandler<TState,TResult> runs once with every item's MapResult<T>. Both live in Platform.Core, so a consumer module needs no dependency on the engine — the Hub owns the worker-side fan-out (checkpoint/resume on retry) and the exactly-once reduce.

Code · How Fan-out / Fan-in Works

How RabbitMQ does fan-out, fan-in

The hard part of Map/Reduce is knowing when all partitions are done so reduce can fire exactly once. The Hub tracks an atomic completion counter; the last map message to ACK trips it and publishes the reduce message.

Fan-out

Coordinator publishes N partition messages to indexing.map; any worker pulls any partition.

Counting done

Each successful ACK atomically decrements a per-batch counter in the shared store — survives worker crashes.

Fan-in → reduce

The ACK that hits zero publishes the reduce message, so ReduceAsync runs exactly once.

Code · Partner Extensibility

Customize jobs with the tools partners already know

Handlers resolve from DI, so partners customize with the tools they already know. Because the enqueue is handler-explicit, the cleanest override is to ship your own handler and enqueue to it; for payload-typed fallbacks, last-registration still wins. Five intents, five idiomatic mechanisms.

// 1 · REPLACE — register your own handler,
// then enqueue to it (handler-explicit)
services.AddBackgroundJob<ReindexProductJob>();  // base
services.AddBackgroundJob<AcmeReindexJob>();      // partner
await jobs.Enqueue<AcmeReindexJob>(payload);   // runs Acme's

// 2 · DECORATE — wrap, keep cross-cutting clean
public class AuditedJob<T>(
    IBackgroundJobHandler<T> inner, IAuditLog audit)
  : IBackgroundJobHandler<T> where T : class
{
  public async Task Execute(T p,
      IJobExecutionContext ctx, CancellationToken ct)
  {
    await audit.StartAsync(ctx.JobId);
    await inner.Execute(p, ctx, ct);
    await audit.EndAsync(ctx.JobId);
  }
}
// 3 · HOOK — subclass, keep base behaviour
public class AcmeReindexJob : ReindexProductJob
{
  public override async Task Execute(...)
  {
    await PreProcess(p, ct);
    await base.Execute(p, ctx, ct);       // platform
    await NotifyAcmeErp(p, ct);
  }
}

// 4 · PIPELINE — many parties, each a step,
// run in module-dependency order

Code · Extending the Payload

Extend the payload with AbstractTypeFactory

Payloads use Virto's signature extensibility mechanism — the same AbstractTypeFactory partners already use to extend CustomerOrder or CatalogProduct. A partner subclasses the payload, registers the override, and their type flows end-to-end through RabbitMQ into their handler with all fields intact.

// Base payload — created via the factory,
// never `new`, so it stays overridable.
public class ReindexPayload : ValueObject
{
  public string CatalogId { get; set; }
  public string StagingIndex { get; set; }
}

// Partner extends with extra fields
public class AcmeReindexPayload : ReindexPayload
{
  public string AcmeRegion { get; set; }
  public bool IncludePreorders { get; set; }
}

// Partner module registers the override
AbstractTypeFactory<ReindexPayload>
  .OverrideType<ReindexPayload, AcmeReindexPayload>();
// Hub always creates via the factory —
// the derived type flows through.
var payload = AbstractTypeFactory<ReindexPayload>
    .TryCreateInstance();

// Envelope carries the CONCRETE type name, so
// the serializer round-trips AcmeReindexPayload,
// not the base — survives the RabbitMQ trip.
envelope.PayloadType = payload.GetType()
    .AssemblyQualifiedName;

// ── No-code alternative ──────────────────
// For light extension without a subclass,
// the payload carries a DynamicProperties bag
// (Virto's built-in mechanism) — extend like
// adding a custom order field in the admin UI.
payload.DynamicProperties.Add(
    "AcmeRegion", "EU-West");

Nothing new to learn. Partners customize jobs with the exact three tools they already use everywhere in Virto — DI override, AbstractTypeFactory, Dynamic Properties. Two guards: payloads stay serializable and additive (add fields, never remove — a job may sit in the queue across a deploy), and the envelope's concrete PayloadType is what the factory resolves on deserialization.
