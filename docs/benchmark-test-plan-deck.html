Overview

Why we're running this

Two engines now ship behind one contract; we need to know which to run where, how much Redis & RabbitMQ memory to provision, and how the worker tier scales — with numbers, not opinions.

The gap

No numbers yet

  • Zero job metrics today — only logs, a health check, and the engine dashboards.
  • Engine choice (Hangfire vs RabbitMQ) is a config switch with no measured trade-off.
  • No sizing basis for Redis / RabbitMQ; no autoscaling story for workers.
The goal

Decide with data

  • Throughput, latency, CPU & memory per 1k jobs for each engine.
  • Memory-sizing formulas for Redis and RabbitMQ.
  • KEDA scale-from-zero design + Pull-vs-Push trade-offs, quantified.
The method

One fair test

  • Instrument the shared dispatch path once → engine-agnostic numbers.
  • Fixed, tunable workloads in the sample module; engine is the only variable.
  • Measure via the existing Application Insights module.
Architecture

The deployment schema we're testing

Same container image, two roles: a Producer (BFF) enqueues; a scalable Worker tier drains. RabbitMQ carries the queue; Redis holds map/reduce batch state.

Hangfire variantNo broker — the Producer enqueues into SQL Server, the Worker runs the Hangfire server polling the same DB, scaled by HPA on CPU (no queue-depth trigger, no scale-to-zero). That asymmetry is a headline result, not a defect.

Sizing & Scaling

Redis sizing — map/reduce only

Redis holds only map/reduce batch state (items list + results hash + meta + checkpoint), 7-day TTL. Footprint scales linearly with batch size and per-item JSON, stored ~twice (input + result).

# per active batch
mem ≈ (Total × itemJSON) + (Total × resultJSON) + meta + checkpoint   # ×1.5–2 overhead

mustSet maxmemory-policy noeviction on the jobs Redis — evicting a batch's items/results mid-run corrupts the reduce (data loss). Size for peak concurrent + abandoned batches (7-day TTL), alert at 80%, and isolate from the platform cache/backplane (dedicated instance or DB index).
Sizing & Scaling

RabbitMQ sizing — backlog drives memory

Broker memory = runtime baseline + queued messages + connections. Persistent classic-queue messages stay in memory until paged; the memory watermark blocks publishers to protect the node.

# broker memory
mem ≈ ~120 MB baseline + (ready+unacked) × (body + ~300 B) + connections

scale-upFor large backlogs, move to quorum / lazy queues (page to disk, bound memory) — the engine declares classic durable queues today. Set disk_free_limit; budget for .dlq depth.
Sizing & Scaling

KEDA — scale the worker tier on queue depth

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
spec:
  scaleTargetRef: { name: vc-jobs-worker }
  pollingInterval: 15
  cooldownPeriod: 300
  minReplicaCount: 0      # scale-to-zero
  maxReplicaCount: 50
  triggers:
    - type: rabbitmq
      metadata:
        queueName: default
        mode: QueueLength
        value: "20"          # msgs per replica
        activationValue: "5"

Tune value to worker capacity. Each replica drains ≈ DispatchConcurrency / avg-job-seconds jobs/s; set the per-replica target to the backlog you tolerate before adding a pod.

Scale-down safety: at-least-once + idempotent handlers; a graceful terminationGracePeriodSeconds to finish in-flight acks; unacked messages requeue on disconnect (honor the cancellation token). Keep PrefetchCount modest so few messages requeue.

Hangfire has no queue-depth trigger → HPA on CPU, no scale-to-zero.

Sizing & Scaling · recommendations

Payload & result recommendations

Payloads = references

The message body is the payload JSON; map/reduce stores each item's JSON in Redis and its result — ~2× amplification. Keep items small (< ~4–32 KB; avoid > 128 KB). Large inputs → blob/DB, pass a key.

Results stay tiny

There's no result path back to the producer — map results flow only to the reducer. The reducer persists the outcome to DB/blob + optional notification; keep per-item results to counts/refs/errors.

Correctness

At-least-once everywhere: handlers idempotent; UniqueKey for dedup; MaxRetryAttempts + DLQ for poison messages. RabbitMQ keeps no status ledger — use progress + metrics.

ruleSmall messages + externalized big data keeps broker & Redis memory predictable and keeps the sizing formulas on the previous slides honest.
