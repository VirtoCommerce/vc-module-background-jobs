What the numbers say

2.6×

RabbitMQ drains map/reduce far faster — at lower CPU

141 vs 55 j/s at 1 core, 282 vs 109 at 2 cores. And it does it at lower peak CPU (1.23 vs 1.73 cores at 2-core) — Hangfire round-trips every child job through SQL, RabbitMQ streams from the broker with a prefetch-gated consumer.

½

Roughly half the CPU per job under sustained load

Both engines hold 200/s with zero failures, but RabbitMQ does it at avg 0.31→0.46 cores vs Hangfire's 0.56→0.95. At 1 vCPU Hangfire peaks at 1.06 cores — momentarily saturating the whole pod, threadpool queue climbing to 43 — while RabbitMQ leaves half the core free.

¼

A quarter of the allocation rate

On the 2-core map/reduce, RabbitMQ allocated 14 MB/s against Hangfire's 58 MB/s — SQL command arguments and job-state churn dominate Hangfire's heap. Less allocation means fewer gen-2 collections and steadier tail latency.

=

Both scale linearly 1→2 cores

RabbitMQ 141→282 (prefetch auto-scales 10→20); Hangfire 55→109 (workers 5→10). Each roughly doubles, so the per-core gap is structural — it holds at every core count, not a tuning artifact.

Method. Single VirtoCommerce platform instance, same benchmark handlers, driven by NBomber; per-process CPU / working-set / GC / threadpool sampled with dotnet-counters. Pod CPU limits simulated with DOTNET_PROCESSOR_COUNT (runtime pool & GC sizing + both engines' self-scaling) plus processor affinity as a physical cap. RabbitMQ ran AutoScaleConcurrency=true, ConcurrencyPerCore=10; Hangfire ran native workers (WorkerCount unset → cores × 5). Map/reduce drain is total-time (2000 jobs ÷ wall seconds). These are relative local numbers for engine comparison — absolute cloud figures need managed RabbitMQ / Redis / SQL on representative nodes. The 0.5-core row was not run (needs a Windows Job Object hard CPU-rate cap).
