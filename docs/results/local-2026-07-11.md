## Headline scorecard

| Dimension | RabbitMQ + Redis | Hangfire (SQL) |
|---|--:|--:|
| Raw drain throughput (burst) | 709 jobs/s | **1411 jobs/s** |
| **CPU per 1k jobs** (sustained 200/s) | **~2.3 core-s** | ~6.9 core-s |
| Working-set peak (sustained) | **374 MB** | 438 MB |
| Alloc under large payload | **287 MB/s** | 961 MB/s |
| Bulk enqueue (10k) | **17.5 s** | 32.2 s |
| External dependencies | RabbitMQ + Redis | SQL Server |
| Scale-to-zero | **yes (KEDA)** | no |

## Findings

1. **CPU efficiency → RabbitMQ.** At the same sustained 200/s, RabbitMQ used ~0.46 avg cores vs Hangfire ~1.38 — roughly **3× less CPU per job** (~2.3 vs ~6.9 core-seconds / 1k). Hangfire's SQL polling + large default worker pool cost CPU even when idle-ish.
2. **Raw drain speed → Hangfire**, but for the wrong reason here: Hangfire's default `WorkerCount` (~cores×N) is much higher than RabbitMQ's `ConsumerDispatchConcurrency=20`. RabbitMQ was **concurrency-bound, not CPU-bound** (burst peak only 1.03/16 cores) — it had huge headroom.
3. **Bulk enqueue is the slow side for both** — per-job confirmed-publish / SQL-insert dominates (RabbitMQ 17.5s, Hangfire 32.2s for 10k). Large payloads make Hangfire enqueue 3× worse (SQL arg blob).
4. **Memory/GC → RabbitMQ lighter** everywhere; Hangfire large-payload is a red flag (961 MB/s alloc, 563 gen2 GCs).
5. **Thread-pool pressure** under sustained load is far higher on Hangfire (queue peak 207 vs 19).
6. **Redis** footprint is negligible for these sizes (fire-and-forget doesn't touch it; map/reduce cleans up after the batch).

## Recommended tuning / next steps

- **RabbitMQ: raise the concurrency knobs.** It left ~90% CPU unused. Re-run `burst`/`sustained` with `ConsumerDispatchConcurrency` 50–100 (and matching `PrefetchCount`) — expect the 709 jobs/s to climb several-fold and likely **beat Hangfire's drain at a fraction of the CPU**. This is the single highest-value change.
- **Hangfire: cap `WorkerCount`** when co-located with the web tier (it's currently out-competing the app for CPU), or move workers to a separate deployment.
- **Add a batch-enqueue path** for bulk producers (both engines) — per-job insert/confirm is the enqueue bottleneck.
- **Enforce small payloads** (references, not blobs) — the 64KB test shows Hangfire GC blowing up; externalize large inputs to blob/DB.
- **Engine pick:** spiky / bursty / idle-heavy workloads → **RabbitMQ + KEDA** (scale-to-zero + CPU efficiency). Always-on, CPU-plentiful, one-dependency simplicity → Hangfire is fine but budget the CPU/memory.
- **Cloud validation** still needed for absolute numbers, KEDA 0→N, and multi-pod scaling.

## Tuning round (RabbitMQ, `ConsumerDispatchConcurrency=64`, `PrefetchCount=20`, + cancellation fix)

| Profile | Throughput | CPU avg / peak | Fails | vs baseline (dispatch=20) |
|---|--:|--|--:|---|
| burst 10k | 763 jobs/s | 0.20 / 0.94 c | 0 | ~unchanged (709) |
| sustained 200/s | RPS 200 | 0.48 / 1.97 c | **1** (was 4) | error storm gone |

**Findings:**
1. **`ConsumerDispatchConcurrency` alone did NOT raise throughput** — `PrefetchCount=20` is the real gate. Prefetch caps how many messages the broker delivers unacked, so effective concurrency stays ~20 regardless of dispatch=64. **To scale RabbitMQ drain you must raise `PrefetchCount`** (e.g. 64–100) with `ConsumerDispatchConcurrency ≥ PrefetchCount`. CPU stayed ~94% idle → huge headroom untouched.
2. **The cancellation fix works** — sustained fails 4→1 (the remaining 1 is a transient, not torn-publish), and the enqueue-cancellation ERROR storm is gone.
3. **Measurement caveat:** the burst "drain throughput" is confounded — the `/fire` call publishes 10k over ~18s while workers drain concurrently, so 709/763 understate the true drain rate and are NOT the concurrency ceiling. A clean drain test needs a **pre-loaded queue** (enqueue first, then start the timer) or per-second registry sampling; recommend adding that to the harness.

**Next to actually prove the win:** set **`PrefetchCount=64`** (+ keep `ConsumerDispatchConcurrency=64`), restart, re-run burst/sustained at a higher rate — expect drain to climb several-fold and CPU to leave idle.

## Code improvements delivered

**#2 — clean drain measurement (harness).** `PollToCompletion` now samples the completion count each second and reports the **PEAK per-second drain rate**, independent of enqueue overlap — so drain throughput is no longer conflated with the (slow) bulk enqueue.

**#3 — batch enqueue (pipelined publisher confirms).** New `IJobEngine.EnqueueBatch` (default loops `Enqueue`; RabbitMQ overrides to issue all publishes under one channel-lock then await confirms together) + a producer facade `IBulkBackgroundJob.EnqueueBatch<THandler>(payloads)`. Micro-benchmark against the live broker (producer-only, 1000 msgs):

| | time | rate |
|---|--:|--:|
| sequential (loop `Enqueue`) | 1691 ms | 591/s |
| **batch (`EnqueueBatch`)** | **55 ms** | **18,182/s** |
| **speedup** | | **30.7×** |

So the ~18s bulk-enqueue of 10k collapses to ~0.5s. Bulk producers (imports, re-index fan-out) should use `IBulkBackgroundJob`. Also fixed: enqueue is now **atomic** (a client disconnect no longer tears an in-flight confirmed publish — the earlier `OperationCanceledException` log spam is gone).

## Tuning round 2 (RabbitMQ, `PrefetchCount=64` + `ConsumerDispatchConcurrency=64`)

| Profile | Result | vs prefetch=20 |
|---|--:|---|
| burst 10k | **enqueue-bound** at 16.7 s (599/s) | unchanged — single confirmed publish caps the producer |
| map/reduce 2000 (fast load, isolates drain) | 4.0 s → **495 jobs/s**, CPU peak 1.44 c (9%) | **2× drain** (was 8.1 s → 246 j/s) |

**Findings (the honest picture):**
1. **`PrefetchCount` is the drain gate — confirmed.** Raising it 20→64 doubled map/reduce drain (246→495 j/s); the earlier `ConsumerDispatchConcurrency`-only change did nothing. CPU stayed ~9% → still huge headroom; higher prefetch (and more worker pods in cloud) would push further.
2. **The producer is confirm-RTT-bound at ~600/s** with single `Enqueue` (burst enqueue 16.7 s for 10k = 599/s, exactly the micro-benchmark's sequential rate). Prefetch doesn't touch this — **`IBulkBackgroundJob.EnqueueBatch` is the producer fix** (30×, above).
3. **Measurement note:** `burst` is enqueue-bound, so its "drain" figure is an artifact (jobs clear *during* the 16.7 s enqueue). **Map/reduce is the clean drain vehicle** (server-side load in ~59 ms). The map/reduce registry updates at reduce time, so use its *total time / avg* (4.0 s / 495 j/s), not the per-second "peak".

**Bottom line:** RabbitMQ's low CPU + `PrefetchCount`-scaled drain + KEDA scale-to-zero make it the efficient choice for spiky/bursty work; pair it with **batch enqueue** for bulk producers. Absolute ceilings + multi-pod scaling still need the cloud round.
