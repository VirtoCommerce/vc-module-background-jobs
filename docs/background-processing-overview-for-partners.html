Why this matters

Problem, solution & value

Problem

Hangfire is hard-wired in

  • Every module imports Hangfire directly — one engine, no choice.
  • SQL-polling doesn't scale on the cloud: work is rejected under load, not queued.
  • No map/reduce for large fan-out (indexing, bulk ops).
  • Idle workers still cost — no scale-to-zero.
Solution

One contract, pluggable engines

  • Engine-agnostic IBackgroundJob abstraction in Platform.Core.
  • Swap the engine by config: Hangfire · RabbitMQ · In-Memory.
  • Built-in map/reduce and recurring jobs.
  • The same handler code runs unchanged on any engine.
Value

Right engine per environment

  • ~2.6× throughput at half the CPU on RabbitMQ vs Hangfire.
  • Scale-to-zero workers via KEDA — pay only for work.
  • No breaking changes — legacy modules keep working.
  • Extend with the same Virto tools partners already use.
What's in the box

Features overview

Everything the platform and partner modules need for background work — behind one small set of contracts in Platform.Core.

01

Engine-agnostic contract

IBackgroundJob / IBackgroundJobHandler<T> — enqueue once, run anywhere.

02

Pluggable engines

Hangfire (SQL), RabbitMQ (+ Redis), In-Memory — selected by configuration.

03

Map / Reduce

Parallel fan-out over items, one reduce — checkpoint/resume, exactly-once.

04

Recurring jobs

Cron or setting-driven schedules; fleet-safe exactly-once firing.

05

Live job progress over SignalR to the admin UI.

06

Retry & dead-letter

Bounded retries with backoff, then a dead-letter queue for inspection.

07

Run RabbitMQ primary while legacy modules keep calling Hangfire directly.

08

KEDA autoscaling

Worker tier scales 0→N on queue depth; App Insights observability.

noteContracts live in Platform.Core; the engine is an installable module. Consumer modules take no dependency on any specific engine.
What's in the box · engines

Supported providers — pick per environment

The same handler code runs on any engine; the provider is chosen by configuration (VirtoCommerce:BackgroundJobs:Provider). Four engines ship today.

Hangfire default · legacy

Durable jobs in SQL Server with the /hangfire dashboard and native recurring. The default engine — legacy modules keep calling it directly.

RabbitMQ cloud

Cloud-scale throughput over an AMQP broker (+ Redis for map/reduce state): DLQ, retry, KEDA scale-to-zero. Recommended for Virto Cloud.

In-Memory dev · test

Zero-infrastructure in-process engine for local development and automated tests — non-durable, single-process.

Google Cloud Tasks sample module

Serverless HTTP-push dispatch on GCP — no worker to run; Cloud Tasks calls your endpoint. Ships as a sample module, released separately.

new engine?A conformance test kit makes writing one safe. Implement IJobEngine, run the shared JobEngineConformanceTests suite — enqueue, retry, status, delete, recurring — and a green run means your engine behaves like the built-ins. It's how all four above are validated.
Architecture

Virto Commerce on Virto Cloud

One container image, three roles. The same Virto Commerce build runs as a storefront BFF, an Admin backend, or a Backend-for-Jobs worker — the role is pure configuration (VirtoCommerce:BackgroundJobs:Mode), not a separate artifact. All instances share one Redis and one SQL.

noteSame image, role by configuration. Every box is the identical Virto Commerce build; Mode picks Producer (enqueue) or Worker (process). Producers scale on CPU/memory (HPA); the worker tier scales on RabbitMQ queue depth via KEDA — 0→N, back to zero (a scaler, never in the message path). All instances share one Redis (progress backplane, cache invalidation, map/reduce state) and one SQL.
Delivery · for partners

Release cycle — no breaking changes

1

Release Platform + BackgroundJobs module

BackgroundJobs goes GA. Hangfire stays the default engine; the new abstraction ships alongside. Nothing breaks — existing modules run untouched.

GA
2.1

Platform updates VC modules

Virto migrates its own modules off direct Hangfire onto the new interface — indexing/search moved to Map/Reduce, recurring jobs onto AddRecurringJob, etc.

2.2

RabbitMQ becomes the primary engine (Provider=RabbitMQ) with EnableLegacyHangfire=true: VC modules run on RabbitMQ, while custom modules keep working on Hangfire — side by side.

3

Partners move custom modules onto the BackgroundJobs architecture at their own pace, then EnableLegacyHangfire=false — a pure RabbitMQ deployment.

promiseEvery step is additive and opt-in. Partners choose when to migrate; legacy and new engines coexist until they're ready.

The C#
developers write

Handlers, recurring schedules and map/reduce — defined against Platform.Core contracts, with no dependency on the active engine. The same code runs on Hangfire, RabbitMQ or In-Memory.

Code · fire-and-forget

A background job in four steps

1Implement the payloadplain class
// A JSON-serializable class — the job's input
public class SendOrderEmailPayload { public string OrderId { get; set; } }
2Implement the job handlerJobs/ folder
// Implements IBackgroundJobHandler<TPayload> — Platform.Core, no engine reference
public class SendOrderEmailHandler(IEmailSender sender)
    : IBackgroundJobHandler<SendOrderEmailPayload> {
    public Task Execute(SendOrderEmailPayload p, IJobExecutionContext ctx, CancellationToken ct)
        => sender.SendConfirmationAsync(p.OrderId, ct);
}
3Register in DIModule.cs
services.AddBackgroundJob<SendOrderEmailHandler, SendOrderEmailPayload>();
4Run it from your codereturns immediately
await _backgroundJob.Enqueue<SendOrderEmailHandler>(new() { OrderId = order.Id });
Code · progress

Report live progress to the admin UI

Long-running jobs stream progress to the admin UI over SignalR — a live progress bar, no polling. Opt in at enqueue time, then report from the handler through ctx.Progress.

// 1 — Enqueue with progress enabled
await _backgroundJob.Enqueue<ReindexHandler>(payload, new EnqueueOptions { ReportProgress = true });

// 2 — Report from the handler — pushed to the admin UI as it runs
public async Task Execute(ReindexPayload p, IJobExecutionContext ctx, CancellationToken ct) {
    for (var i = 0; i < p.Total; i++) {
        await Reindex(p.Items[i], ct);
        await ctx.Progress.Report(new JobProgressInfo {
            Message = $"Indexed {i + 1}/{p.Total}", ProcessedCount = i + 1, TotalCount = p.Total }, ct);
    }
}
UXThe platform turns each JobProgressInfo into a live notification — the admin sees a progress bar with a message and count while the job runs, and a completion state at the end. Fire-and-forget jobs simply skip this.
Code · extensibility

Customize & extend — no platform fork

Jobs are defined against Platform.Core contracts and resolved from DI — so a partner extends them from their own module: enrich the payload, or replace the handler. The last registration wins, so your version overrides the platform default with no fork or patch.

① Enrich the payload

Subclass the platform payload (or define your own) with the extra fields your handler needs — the enqueue call carries them through unchanged.

② Replace the handler

Register your own IBackgroundJobHandler<T> for the same payload. Registered later, it wins — the platform's handler is transparently overridden.

// In YOUR module — enrich the payload…
public class MyOrderEmailPayload : SendOrderEmailPayload { public string CampaignCode { get; set; } }

// …and replace the handler (registered later → your handler wins)
public class MyOrderEmailHandler(IEmailSender sender, ICampaigns campaigns)
    : IBackgroundJobHandler<MyOrderEmailPayload> { /* your logic */ }

services.AddBackgroundJob<MyOrderEmailHandler, MyOrderEmailPayload>();  // overrides the default
Code · recurring

Recurring jobs — a handler + a schedule

A recurring job is a handler + a schedule. Fixed cron, a fixed or per-run payload, or setting-driven — so admins change the schedule without a redeploy.

// Fixed cron — every 6 hours
services.AddRecurringJob<ReindexCatalogJob, ReindexPayload>(s => s.WithCron("0 */6 * * *"));

// Pass a fixed payload each occurrence
services.AddRecurringJob<SendDigestJob, SendDigestPayload>(
    new SendDigestPayload { Top = 10 }, s => s.WithCron("0 8 * * *"));       // daily 08:00

// …or build a fresh payload per run (e.g. a timestamp)
services.AddRecurringJob<SnapshotJob, SnapshotPayload>(
    () => new SnapshotPayload { AtUtc = DateTime.UtcNow }, s => s.WithCron("*/15 * * * *"));

// …or setting-driven: enabler + cron come from module settings
services.AddRecurringJob<ProcessSubscriptionJob, ProcessSubscriptionPayload>(
    s => s.FromSettings(enabled: Settings.EnableProcessJob, cron: Settings.ProcessJobCron));
fleet-safeExactly-once firing across instances via a distributed lock + a shared occurrence marker (Redis in the cloud). On Hangfire, recurring uses its native scheduler + dashboard.
Code · settings

Cron as a first-class setting type

Setting-driven schedules (FromSettings) need a cron an admin can change safely — so cron becomes a first-class platform setting type, SettingValueType.Cron.

Problem

Hand-typed cron strings

  • Cron lives in a free-text setting — a typo ships a broken schedule.
  • No validation on save; no hint what 0 */6 * * * means.
  • Admins guess the syntax; support tickets follow.
Solution · SettingValueType.Cron

Validated, guided, described

  • Validated on save — an invalid expression is rejected.
  • Admin editor with presets + a live plain-English description (dCron).
  • Consumed directly by AddRecurringJob(…FromSettings).
// Declare a cron setting — validated on save, edited with presets + a live description
new SettingDescriptor {
    Name = "MyModule.ProcessJobCron", GroupName = "MyModule|Jobs",
    ValueType = SettingValueType.Cron, DefaultValue = "0 */6 * * *" }
Code · map / reduce

Map / Reduce — big fan-out, done right

Reindex, recalc prices, bulk export — 10k+ items. One serial job is slow and loses all progress on a crash. Map/Reduce fans the work across the fleet and reduces once.

howThe Hub owns coordination. Each Map is checkpointed in Redis — a retried or crashed worker resumes, never repeats — and when the last item finishes the Reduce fires exactly once. A module implements just two interfaces; fan-out, resume and exactly-once come for free.
Code · map / reduce

Map / Reduce in three steps

1Define the handler for one operationIMapJobHandler
// MAP — runs per item, in parallel across the worker fleet
public class IndexPageHandler : IMapJobHandler<IndexPage, PageResult> {
    public Task<PageResult> Map(IndexPage page, IJobExecutionContext ctx, CancellationToken ct) { /* index one page */ }
}
2Define the handler for the reduce (summary)IReduceJobHandler
// REDUCE — runs once, with every item's result (success or failure)
public class IndexSummaryReducer : IReduceJobHandler<IndexState, PageResult> {
    public Task Reduce(IndexState state, IReadOnlyList<MapResult<PageResult>> results, ...) { /* persist summary */ }
}
3Split into batches and runfrom your code
services.AddMapReduceJob<IndexPageHandler, IndexSummaryReducer>();
await _mapReduce.Enqueue<IndexPageHandler, IndexSummaryReducer>(pages, new IndexState());
errorsError handling is built in. A failing Map is retried with backoff; after the attempt limit it's dead-lettered and recorded as a failed MapResult — the batch keeps going. Reduce receives every result and decides how to finish (fail, partial-commit, or report). Checkpointing means a crashed or retried worker resumes, never repeats.
Code · REST API

Initiate a handler over REST

There's no generic "run any job" endpoint. Your module exposes its own typed controller that injects IBackgroundJob and enqueues — you keep your routes, auth and payload contract; the platform provides an engine-agnostic endpoint to poll status.

// Your module's controller — inject IBackgroundJob, enqueue, return the job id
[Route("api/my-module/jobs")]
public class MyJobsController(IBackgroundJob backgroundJob) : Controller {
    [HttpPost("send-email")]
    public async Task<ActionResult<string>> Send([FromBody] SendOrderEmailPayload p, CancellationToken ct)
        => Ok(await backgroundJob.Enqueue<SendOrderEmailHandler>(p, ct));   // → engine job id
}
…then call it, and poll status on the platform's engine-agnostic endpoint
POST /api/my-module/jobs/send-email     → "a1b2c3d4"   (engine job id)
GET  /api/platform/jobs/a1b2c3d4        → { "id": "a1b2c3d4", "completed": false }
APIThe platform ships a read-only monitor — GET /api/platform/jobs/{id} — that reads status from the active engine (Hangfire, RabbitMQ, …) behind the BackgroundJobsManage permission. Enqueue stays in your controller, typed to your payload.
Performance · measured

Hangfire vs RabbitMQ — measured

Same workload, same handlers, engine is the only variable. Local runs at pinned CPU limits; cloud on a 1-vCPU Azure App Service (B1), read from Application Insights.

MetricHangfire (SQL)RabbitMQ + RedisAdvantage
Map/reduce drain — local 1 core55 j/s141 j/s2.6×
Map/reduce drain — local 2 core109 j/s282 j/s2.6×
Map/reduce drain — cloud 1 vCPU24 j/s131 j/s5.5×
CPU — sustained 200/s (cloud)saturates (~100%)~1%idle
Memory — worker under load (cloud)grows with backlogflat · boundedstable
whyHangfire round-trips every job through SQL; on the cloud that latency dominates and the producer rejects work under load. RabbitMQ enqueues with a cheap broker publish, and prefetch caps in-flight work — so a 1-vCPU pod absorbs 200/s at ~1% CPU with flat, bounded memory, then scales out on queue depth with KEDA.
Observability

Logging & observability

Every job is traceable end-to-end — structured logs through the run, metrics and events into Application Insights, and readiness on /health.

01

Structured lifecycle logs

Enqueued → started → succeeded / failed / retried, each tagged with job id, handler, queue, attempt.

02

App Insights metrics

jobs/execution.duration.ms and jobs/queue.latency.ms, plus a JobCompleted event.

03

Failure diagnostics

Exceptions logged with context; the poisoned message lands in the dead-letter queue with headers for inspection.

04

Health & readiness

/health reports engine readiness and flags a queue engine running on an in-memory store.

noteTelemetry is inert by default — job telemetry depends on an optional TelemetryClient, so metrics and events flow only once the platform's Application Insights module is installed. Logs always flow through the standard ILogger pipeline.
